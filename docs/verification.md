# Verification

[DESIGN.md](../DESIGN.md) owns game rules and milestone scope.
[TODO.md](../TODO.md) tracks M1 implementation and acceptance work. Existing
mission flows exercise the playable ARC M0 slice; they do not establish M1
skirmish acceptance. These checks cover the application, authored mission,
and desktop host. Automated runs establish correctness; human runs establish
clarity, pacing, and usability.

## Automated checks

Use two check tiers:

- `npm run check` during development and before completing a coding task. It
  checks formatting, TypeScript and Rust linting and types, all non-asset unit
  tests, and four Chromium browser smoke checks. These cover title-screen
  options and session startup, generated model loading, construction and
  training with mouse and phone touch, and guide/save/load/restart integration.
- `npm run check:full` before committing. It adds generated-asset checks, the
  Rust test harness, every browser flow in Chromium, and the `@webkit` browser
  flows in macOS WebKit, including phone/tablet layouts and complete M0
  playthroughs. The Rust harness currently has no tests; platform adapters have
  TypeScript tests.

`npm test` runs the quick tests without formatting, linting, or type checks.
`npm run test:full` runs all tests. Both tiers use at most two unit workers and
one browser worker, leaving CPU capacity for the editor and game. Override them
for a focused run with Vitest's `--maxWorkers` or Playwright's `--workers`.

For narrower feedback:

```sh
npm run test:watch                         # non-asset units, watch mode
npm run test:ts:quick -- tests/combat.test.ts
npm run test:ts -- --project=assets        # asset contracts and regeneration
npm run test:visual:quick                  # four Chromium smoke checks
npm run test:visual -- e2e/saves.spec.ts --project=chromium
```

Asset changes need the asset project; browser, input, layout, or platform
changes need the affected full browser specs as well as the quick tier. A quick
pass does not establish full cross-engine or mission acceptance.

Install Playwright browsers once with `npx playwright install chromium`, plus
`webkit` on macOS. Checks use full headless Chromium with GPU WebGL; macOS also
runs `@webkit` checks to cover the desktop webview engine. The headless shell's
software WebGL can time out under parallel load. Browser checks write
screenshots and attachments to `playwright-report/`. Some use `e2e/harness.ts`
to inspect views or drive a controlled simulation clock.

Browser checks start their own Vite server on `127.0.0.1:4173`, separate from
the development server. Set `COTUW_TEST_PORT` if that port is occupied. Checks
never reuse an existing server, which could serve another checkout.

The GitHub Actions Check workflow runs only by manual request to conserve the
monthly quota. It runs the full tier on macOS, all TypeScript and Rust checks
without browsers on Windows, and all TypeScript checks on Linux.

Build browser and native artifacts with:

```sh
npm run build
npm run tauri build -- --debug --no-bundle
npm run tauri build
```

Regenerating assets and levels with `npm run assets` and `npm run levels`
should leave committed output unchanged unless their sources changed.

## Coverage ownership

- Unit tests own simulation rules, edge cases, deterministic continuation,
  serialization, and presentation calculations. Prefer these for new rule
  combinations instead of repeating them through browser interactions.
- `tests/**/*-assets.test.ts` belong to the full-only `assets` project. They
  verify generated bytes, texture/audio contracts, and exported model behavior.
  Other `tests/**/*.test.ts` files enter the quick `unit` project automatically.
  The projects are disjoint; a full run executes each unit test once.
- Browser specs own real input, DOM focus/layout, WebGL rendering, browser
  audio, and application wiring. Retain browser checks that can fail while the
  corresponding unit test passes. Screenshots attached to reports are review
  artifacts; most checks assert behavior rather than compare image baselines.
- The complete `e2e/mission.spec.ts` flow owns the authored economy-to-victory
  progression, victory, and free-play construction and production with mouse
  and phone touch. Focused economy specs cover distinct interactions such as
  training cancellation/refunds, rally points, support loss, and loading saved
  goal progress.
- Startup checks verify generated model readiness, browser errors, and that
  title-screen volume and mute settings carry into a session. Audio control
  specs own every bus setting and its persistence across restart and reload.
- Check shared textures once per file and clip pair. Different clips in one
  sheet have different cell edges. Reuse decoded pixels across seam, alpha,
  minimap, and effect contracts. Byte-for-byte generation and those contracts
  detect different failures and both belong in the full tier.
- Browser tags live in `e2e/tags.ts`. Keep `QUICK` limited to representative
  integration flows. Add browser coverage to the full suite by default; add a
  quick tag only for a missing smoke responsibility. Reuse an existing check in
  both tiers.
- Tag a browser check `WEBKIT` when it exercises WebGL rendering, audio,
  pointer, touch, wheel, or keyboard events, focus, layout, or browser storage
  and files. Leave simulation wiring and DOM lifecycle checks Chromium-only.
- Declare viewport and input variants with `forEachProfile` from
  `e2e/profiles.ts`. Use compact phone input for a representative touch flow.
  Add tablet cases for layout differences, and repeat input modes where they
  expose distinct behavior. Avoid duplicating long progression to test one
  control.

To audit growth, use `npm run test:ts -- --reporter=verbose` for unit timings
and the Playwright HTML report for browser durations. Compare runs on the same
machine without concurrent test suites. Review slow checks for repeated setup,
asset decoding, progression, and assertions already owned by another test
before increasing worker counts or timeouts.

## Mission flow

The full ARC M0 browser mission starts at the title screen and uses the authored
economy, actors, combat, and objectives through victory and free play. It runs
with mouse and phone touch input in Chromium and WebKit. Its controlled clock
accelerates waiting without granting resources or changing balance.

```sh
npx playwright test e2e/mission.spec.ts
```

Run the same strategy with the app's normal timers and render loop:

```sh
COTUW_REALTIME_PLAYTHROUGH=1 npx playwright test e2e/mission.spec.ts \
  --project=chromium --grep mouse
```

## Human acceptance

- Have RTS-familiar first-time players attempt the ARC M0 mission using in-game
  guidance. Observe the economy bootstrap, Harvester assignment, controls,
  route discovery, army preparation, and den assault. Record completion time,
  pauses, speed changes, confusion, assistance, and abandonment. Fix recurring
  blockers and repeat the affected paths. Aim for the design's 5 to 10 minute
  successful run without slowing the economy or adding encounters to pad it.
  M1 match-length and skirmish acceptance targets are separate tasks in TODO.md.
- On a fixed revision, run the built Windows and macOS apps from the title
  screen through victory and continued free play. Exercise defeat, load,
  restart, Main menu, and Exit. Check the default 800×600 window and resizing,
  keyboard and pointer controls, audio, and returning after Alt-Tab.
- Verify named saves survive relaunch, repeated quicksave overwrite and
  quickload, objective autosave, native Import and Export, cancellation, and
  malformed or incompatible files preserving the current session.
- Check Options before starting a mission and confirm settings persist through
  loads, restarts, and relaunch. Listen for the mix and loops throughout a run.
- Test release bundles and installation when distributing the desktop demo.
  Compilation and browser WebKit checks do not verify packaged-app behavior.

Include the revision, platform, build mode, input method, observed result, and
reproduction details with actionable bug reports. Track work in issues and
commit history rather than keeping dated acceptance logs in project docs.
